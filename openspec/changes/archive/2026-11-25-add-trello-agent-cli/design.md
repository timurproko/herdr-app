# Design

## Context

See `proposal.md` for motivation and scope. The scout's section 4 is the starting architecture, narrowed by the owner's decisions.

Observed repository boundaries:

- `tools/plugins.mjs` discovers `src/plugins/<id>/plugin.js`, packages ordinary plugin-folder helpers into plugin consumers and discovers local `*.test.mjs` tests. No `panel.json` is needed for a headless plugin.
- `src/plugins/registry.js` owns `custom.plugins` enablement/settings and supports `defaultEnabled: false`. `docs/PLUGIN-UI.md` requires declarative status/settings, not custom Settings rendering or secret text fields.
- `tools/core-ci-monitor.mjs` demonstrates narrowly reading persisted `shared.json` plugin state from a standalone Node process. Trello must not rewrite it or inspect unrelated account data.
- `tools/build.mjs` maps `lib/` dependencies into `.customizations/runtime/`; `tools/deploy.mjs` owns conflict checks, locking, hashes and backup/recovery. Neither currently installs a PATH CLI. Runtime packaging alone therefore does not meet the requested shell discovery outcome.
- Shell-only deployment explicitly installs four shell files and must remain unchanged. Full deployment can add Trello payload and separately owned launchers; it must not imply remote token provisioning.

## Goals / Non-Goals

**Goals:** A built-ins-only Node operation engine shared by the CLI and small plugin status worker; private authority that cannot be granted by portable preferences; fixed typed routing; reproducible fake-transport tests; source-independent installation.

**Non-Goals:** A Trello Power-Up UI, token broker, protected identity separate from the OS user, native changes, cloud infrastructure, MCP, persistent card cache or additional refresh scheduler. The owner's permanent-deletion exclusion also removes the scout's optional checklist/check-item deletion. Existing-label assignment/removal is not board-label administration.

## Decisions

### 1. Keep all Trello behavior in one plugin folder

Use `plugin.js`, `actions.js`, `config.js`, `setup.cjs`, `credentials.cjs`, `policy.cjs`, `client.cjs`, `operations.cjs` and `cli.cjs`, with plugin-local tests. Helpers may be consolidated where useful, but no copied Git relay/Core-monitor implementation or peer-plugin dependency. App modules import only their plugin API and local helpers. Runtime copies are build outputs from these canonical files.

The declaration defaults disabled and declares a public `access` choice defaulting to `read-only`; a public read-write selection is only an additional restriction/preference, never authority. Prerequisites show installed/configured/scope status through sanitized local worker output. Checking Settings does not contact Trello, generate a token, import credentials or enable writes. Local setup is documented rather than a secret-bearing Settings form or an Install all action.

Alternative rejected: adding a generic tool registry or a custom board panel. Neither is required for shell agents and both broaden this change.

### 2. Private host-local credential and policy stores

Resolve home using an explicit non-secret home selector, otherwise nonempty `HERDR_APP_HOME`, otherwise `~/.config/herdr-app`, consistent with deployment. Store only:

- `.customizations/trello/credentials.json`: version, API key, user token.
- `.customizations/trello/policy.json`: version, canonical allowed board-ID array and `allowWrites: false` by default.
- Optional `.customizations/trello/cooldown.json`: bounded non-secret retry deadline/reason only, never Trello text or an authenticated URL.

Explicit `setup` accepts protected JSON stdin/input-file content, never `--key`, `--token` or environment credential fallback. Separate typed local policy commands add/remove exact board IDs and enable/disable writes; no wildcard. Credentials are not generated by deployment. Rotation is explicit, schema-checked and guarded against concurrent/unknown files. Setup defaults to an empty allowlist and read-only, preserving existing valid policy unless explicitly changed. Setup and policy management are local administrative actions available even while the plugin is off; they make no Trello request.

Refuse source-checkout targets, symlink/reparse traversal, nonregular files, unsupported schemas and unsafe ACLs/modes. Use owner-only directory/file permissions (0700/0600 on Unix); establish and verify restrictive current-user Windows ACLs, allowing necessary OS administration principals but not broad user groups. Fail closed if protection cannot be verified. Use exclusive creation and guarded atomic replacement, preserving private permissions across rotation. Never silently repair a malformed existing secret store or read installed credentials during development.

Every data request rereads only the current plugin state, access setting and private policy; missing/malformed state denies access. Writes require enabled plugin, public read-write mode, local `allowWrites`, an explicit allowed board and server token capability. Before each network follow-up and immediately before dispatch, compare current authority with the captured operation policy. A preflight read never authorizes a later write after reconfiguration. On revocation or generation mismatch, discard obsolete read results and stop follow-ups; an accepted mutation can still finish and must retain truthful outcome reporting.

Alternative rejected: secrets in hidden plugin settings, token flags, account-wide board discovery or public board/write settings as the only gate.

### 3. Typed JSON commands and fixed-origin transport

Provide human-readable `--help` plus versioned JSON for status, administrative results and data operations. Use one result object per invocation, stable exit categories and no interleaved progress output. Proposed envelope: `{version:1,ok:true,data,...}` or `{version:1,ok:false,error:{code,message,outcome,retryAt?}}`. Distinguish definite local refusal, definite HTTP rejection and unknown mutation outcome. Transport injection is a module/test dependency, never an exposed CLI URL, module or arbitrary-request option.

Representative commands:

- `boards list`, `lists list --board ID`, `cards list --board ID [--list ID]`, `cards get ID --board ID`.
- `cards create/update/move/archive`, `comments add`, `labels list`, `cards label add/remove`.
- `checklists list/add/update`, `checkitems list/add/update`; update supports complete/incomplete as well as rename/position.
- JSON mutation bodies via stdin or `--input <file>`; all child operations carry explicit board and parent IDs. No fuzzy name resolution, batching, card/checklist copying, custom methods or unknown fields.

All requests go through one injected transport with fixed base `https://api.trello.com/1`, query `key` and `token` inserted internally, redirect rejection, an operation route/field allowlist and no external URL fetches. Mutation fields use documented query/body encodings and bounded JSON input, never shell subprocesses. Validate canonical IDs, names, descriptions, dates, booleans and positions before transport. Reject caller-supplied `key`, `token`, attachments, source-copy fields and unrelated native parameters even when the API supports them.

Initial local safety limits: 256 KiB input, 2 MiB response, 20-second request timeout, 60-second command budget, at most three read requests concurrently, at most 20 requests per command and one mutation. Default list/comment page size 50 with maximum 100; use documented continuation, not automatic full-history traversal. Return per-component `complete`/`truncated` facts and continuation metadata. Lists/checklists/items without a supported remote cursor use explicit capped/incomplete results, not invented server pagination. These are client bounds, not claims about Trello quotas.

Do not automatically retry any dispatched mutation, even nominally idempotent updates. Timeout, disconnect, response-size failure or malformed success after dispatch can mean `outcome: unknown`; provide read-based reconciliation guidance. For simplicity, initial reads also return errors without automatic retries. HTTP 429 persists a sanitized host-local cooldown respecting Retry-After (seconds or HTTP date) and the applicable rate interval, with a conservative fallback when absent. No background wakeup or replay queue. Authentication/permission/not-found errors remain distinct, and raw provider messages, stacks and authenticated URLs never reach JSON/stderr/logs.

### 4. Enforce board scope before child lookup

`boards list` reads each allowlisted board directly; it never calls `/members/me/boards` and filters afterward. The owner supplies canonical board IDs during local policy setup.

For child commands, first validate the explicit board against current local policy. Resolve list/card membership only from that board's scoped lists/cards; verify label IDs using that board's labels and checklist/item IDs using the already verified card's checklists. An unrecognized child ID is refused without an arbitrary `/cards/{id}` or `/lists/{id}` lookup. Membership pagination is bounded; inability to prove membership is a refusal, not a fallback to unrestricted lookup. Re-read minimal membership immediately before mutation and recheck returned board/card identities before publishing content or starting follow-ups.

Card updates expose name, description, due/start, dueComplete and position only. Moving is a separate operation, with explicit destination board/list, both boards in scope, and one `PUT` with `idList` and (only for a cross-board move) `idBoard`. Labels are added/removed separately, after proving their board identity. Archiving uses `closed: true`; no permanent-delete route is exposed. Checklists support add/name/position; items support add/name/position/state. Member administration, advanced check-item due/assignment and unarchive are not required in this first catalog.

Trello has no cross-request scope lock. Board-scoped preflight and returned-identity checks mitigate forged IDs and ordinary movement but cannot stop an external actor moving a card between requests. Disclose the race rather than claiming this client is an atomic security boundary.

### 5. Official endpoint contract

The following routes and fields were checked against Atlassian's official REST reference and its linked OpenAPI document while preparing this plan. No API operation was sent. Recheck this contract when implementing; the scout table is not endpoint evidence.

Sources:

- [Authorization](https://developer.atlassian.com/cloud/trello/guides/rest-api/authorization/): API key tied to a Power-Up; user authorization at `https://trello.com/1/authorize` with `response_type=token`, chosen expiration and `scope=read` or `read,write`; query authentication uses `key` and `token`. No OAuth application secret is needed.
- [API introduction and paging](https://developer.atlassian.com/cloud/trello/guides/rest-api/api-introduction/): lists of cards/actions are capped at 1000; `before`/`since` accept creation dates or IDs. Avoid assuming offset pagination.
- [Cards](https://developer.atlassian.com/cloud/trello/rest/api-group-cards/), [Boards](https://developer.atlassian.com/cloud/trello/rest/api-group-boards/), [Lists](https://developer.atlassian.com/cloud/trello/rest/api-group-lists/), [Checklists](https://developer.atlassian.com/cloud/trello/rest/api-group-checklists/).
- [Official linked OpenAPI](https://dac-static.atlassian.com/cloud/trello/swagger.v3.json?_v=1.1274.0): server is `https://api.trello.com/1`; route summaries and parameter schemas below were inspected directly. Some collection schemas omit paging parameters; the introduction/nested-resource guidance must be considered with the route reference, not filled in from memory.
- [Rate limits](https://developer.atlassian.com/cloud/trello/guides/rest-api/rate-limits/): 300 requests/10 seconds per key, 100/10 seconds per token; use token/key interval and remaining-count response headers. Shared-account callers can consume these budgets independently of this CLI.

| CLI behavior | Documented method/path | Restricted inputs/notes |
|---|---|---|
| Allowed boards | `GET /boards/{id}` | `fields=name,url,closed`; explicitly disable unneeded nested resources, including default lists/actions |
| Lists and membership | `GET /boards/{id}/lists` | `filter`, `fields`; no board/list creation |
| Cards and membership | `GET /boards/{id}/cards` | Bounded selected card fields and documented card paging/filter controls |
| List cards | `GET /lists/{id}/cards` | Only after board/list membership verification |
| Card detail | `GET /cards/{id}` | Selected fields; attachments, plugin data, stickers and unrelated nested resources disabled |
| Comments | `GET /cards/{id}/actions` | `filter=commentCard`; reference also declares `page` with maximum 19; use documented before/since paging from the introduction and expose incompleteness |
| Checklists/items | `GET /cards/{id}/checklists` | `checkItems=all`, bounded supported fields; includes item state |
| Existing board/card labels | `GET /boards/{id}/labels`, card `labels` field | Labels route supports `fields` and limit up to 1000; never create/update board labels |
| Create card | `POST /cards` | `idList` required by API; client additionally requires name; optional desc/dates/pos; no attachments/copy sources |
| Update/move/archive | `PUT /cards/{id}` | Restricted update fields; separate move uses idList/idBoard; archive uses closed=true |
| Add comment | `POST /cards/{id}/actions/comments` | Required `text` |
| Assign existing label | `POST /cards/{id}/idLabels` | Client requires `value` label ID although schema marks it optional |
| Remove assigned label | `DELETE /cards/{id}/idLabels/{idLabel}` | Removes association, not the label/card |
| Add checklist | `POST /cards/{id}/checklists` | `name`, `pos`; no `idChecklistSource` |
| Edit checklist | `PUT /checklists/{id}` | `name`, `pos` only |
| Add check item | `POST /checklists/{id}/checkItems` | Required `name` (API 1–16384 chars), optional pos/checked |
| Edit/complete check item | `PUT /cards/{id}/checkItem/{idCheckItem}` | name/pos/state; state complete/incomplete, verified checklist membership |

Permanent card, checklist and check-item delete endpoints exist in the reference but are intentionally absent from the CLI. No generic REST adapter exposes them indirectly.

### 6. Install a real shell command, not a source forwarding script

Map CLI dependencies explicitly to `lib/trello/` runtime outputs in `customization.json`; plugin discovery still owns mod-local copies. Extend full deployment with an exact-name user-bin launcher installer, default `~/.local/bin/herdr-trello` for Bash/POSIX and `herdr-trello.cmd` for Windows command/PowerShell shells. Generated launchers bind the selected installed runtime home and pass arguments without shell evaluation. Paths with spaces and non-ASCII text need fixture coverage.

Use a narrow user-bin ownership sidecar and journal tied to the resolved Herdr home: exact allowed filenames, before/after hashes, install lock, atomic replacement, later-edit refusal and rollback/removal support. Preflight launcher conflicts before unrelated payload writes. Do not extend the runtime path validator into a generic outside-home path writer. A different Herdr home cannot silently replace another home's launcher. No global npm package or changing mod-copy path is the canonical entrypoint.

Require the chosen user bin to be on the deploying shell's PATH, or fail early with an actionable owner instruction to add it and rerun normal deployment. Do not edit profiles, global/user PATH configuration or running process environments. This matches the machine's existing user-bin convention and keeps installation explicit; disposable tests inject their own user bin and PATH. Document that existing agents may need an explicit environment refresh/new shell if their inherited PATH lacks that directory; do not restart them automatically. A full deploy installs CLI files even with Trello disabled, but setup and all remote access stay opt-in.

Alternative rejected: silently relying on `node <checkout>/...`, only installing an unreachable runtime script, or writing shell functions from the directory-reporting hook (which intentionally ignores captured tool shells).

## Risks / Trade-offs

- [Same-user agents can bypass local files/policy] → Document explicitly; recommend a read-only Trello token for server-enforced read-only use, and a minimally privileged Trello account. Stronger isolation needs another OS identity/broker and is excluded.
- [Query authentication can leak through URLs] → Never launch curl, print request URLs, follow redirects or forward raw errors; redact fake secrets in adversarial tests. Owner deliberately chose this documented auth mode.
- [Concurrent card moves can race membership checks] → Verify before dispatch/after response, fail closed on mismatch and disclose lack of atomic Trello scope enforcement.
- [Launcher installation adds outside-home ownership] → Exact-name sidecar/journals, conflict preflight, disposable-bin tests, and no arbitrary destination escape hatch or profile changes.
- [Private-file protection differs on Windows] → Verify ACLs rather than assuming chmod provides isolation; refuse unsupported protection. Administrative OS principals are not a promise of protection from administrators.
- [API pagination schemas are incomplete] → Use the official introduction alongside the route reference, test exact requests and explicit partial results, and do not advertise undocumented continuation or full-history guarantees.
- [No real API acceptance in this task] → Inject transport for every regression and state that route confirmation is documentation-based, not live authentication or board-write proof.

## Migration Plan

1. Ordinary build packages plugin declarations and runtime dependencies; full deploy installs owned runtime plus conflict-checked user-bin launchers. No stores are read or provisioned by build/deploy. Shell-only paths remain untouched.
2. Owner generates a token for their API key using Trello's explicit authorization page, imports it locally, adds board IDs and enables the plugin. Initial use stays read-only. Write use separately requires public read-write mode, local write opt-in and a suitable user token.
3. Each other execution host needs its own full installation and explicit local provisioning; neither deploy:all's shell-only peers nor portable preferences transport tokens or scope authority.
4. Disabling the plugin stops new data work. Revoking the token at Trello removes server access; local credential removal alone does not revoke it. Local rotation/reconfiguration never retries an uncertain write.
5. Rollback/removal uses recorded owned runtime/launcher hashes and refuses later personal changes; private credential/policy files remain until the owner explicitly removes them.
